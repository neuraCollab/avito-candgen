# Кандидатогенерация для поиска услуг Авито

Задача: для каждого из 2452 поисковых запросов выбрать из корпуса 189 212 объявлений
до 50 кандидатов так, чтобы в них попали объявления, которые выбрал пользователь.
Метрика — Recall@50.

**Результат на платформе: Recall@50 = 0.9081** (`answer.csv` в корне репозитория).
Локальная валидация, устроенная как бенчмарк: 0.940 на отложенном фолде, 0.935 out-of-fold.

```
запрос ──► сигналы релевантности по всему корпусу ──► пул ~420 кандидатов ──► LightGBM-ранкер ──► top-50
            BM25 · похожие запросы train ·              7 источников             ~60 признаков
            3 bi-encoder'а · локация                    полнота пула 0.966
```

## Быстрый старт

```bash
python -m venv .venv
.venv/Scripts/pip install torch==2.14.0 --index-url https://download.pytorch.org/whl/cpu
.venv/Scripts/pip install -r requirements.txt
# положить train.parquet, benchmark_queries.parquet, benchmark_items.parquet в data/
.venv/Scripts/python src/fetch_models.py   # веса моделей из релиза (~370 МБ)
.venv/Scripts/python run_all.py            # ~2 часа на 8-ядерном CPU -> answer.csv
```

`run_all.py` пересчитывает всё с нуля: валидационные фолды, индексы, эмбеддинги, кандидатов,
признаки, ранкер. Из готового берутся только веса двух дообученных нейросетей: их обучение
на CPU не воспроизводится бит в бит.

Контрольный повторный прогон в чистом каталоге побайтно совпал с исходным на всех проверенных
этапах: валидационные фолды и fit-часть train, корпуса, BM25-индексы, эмбеддинги rubert-tiny2
для всех 201 008 объявлений и запросов. Остальные шаги устроены так же детерминированно:
фиксированные seed в выборке фолдов и в ранкере, фиксированный порядок батчей и число потоков. `python run_all.py --retrain` обучает их заново
(~7 часов; `python src/fetch_models.py --base` докачает базовую модель), результат при этом может
отличаться в третьем знаке. GPU и внешние API не нужны.

## 1. Данные и признаки

### Что показал анализ данных

| Наблюдение | Вывод для решения |
|---|---|
| Все 2452 текста запросов бенчмарка уникальны, и только 37% из них встречаются в train. У случайного *уникального* текста train доля повторов в train ~40%. | Бенчмарк — это «хвост», примерно один запрос на уникальный текст. Запоминать train нельзя, нужно обобщать. |
| Объявления корпуса почти не пересекаются с train (5–10%), при этом снимок их признаков тот же (на 18k общих объявлений все поля совпадают). | Признаки уровня `item_id` («сколько раз выбирали») бесполезны. Нужно сопоставлять содержание. |
| 76–83% выбранных объявлений находятся в той же локации, что и поиск. Остальные — в «дочерних» локациях: поиск по области → объявление в городе области. | Локация — главный фильтр. Переходы «локация поиска → локация объявления» берём из train. |
| Число объявлений в локации пропорционально числу запросов бенчмарка в ней (~60–77 на запрос, корреляция 0.93), и они тематически близки к запросам. Для «арзамас дивеево такси» в корпусе почти одни трансферы и такси. | Корпус собран «вокруг запросов», похоже на выдачу поиска. Правильный ответ конкурирует с десятками похожих объявлений из своей локации, поэтому ранжирование внутри темы важнее отсева чужих тем. |
| Фильтры поиска (`Вид услуги …`, `Тип услуги …`) дословно встречаются в параметрах выбранного объявления. | Совпадение фильтров с параметрами объявления — отдельный признак. |
| ~1% объявлений корпуса — не из категории услуг (114). В train они почти никогда не бывают ответом. | Признак категории. |

### Какие данные используются

- **Объявления:** заголовок, параметры (`item_infm_params_text`), описание (первые 400 слов:
  хвосты длинных описаний — в основном SEO-шум), подкатегория, локация и координаты, рейтинг,
  отзывы, цена, флаги.
- **Запрос:** текст, локация, фильтры. `search_category` почти всегда 114, а поиска с доставкой
  в бенчмарке нет, поэтому оба поля не используются.
- **train:** только как «память»: какие подкатегории и формулировки выбирали по похожим
  запросам, как связаны локации, пары «запрос → объявление» для дообучения нейросетей.

### Признаки ранкера (`src/candidates.py`) и зачем они нужны

| Группа | Признаки | Зачем |
|---|---|---|
| Лексические | BM25 по заголовку / параметрам / описанию; доля слов запроса в каждом поле; доля биграмм запроса, стоящих рядом в заголовке; «точность» заголовка (доля его слов из запроса); символьная близость (n-граммы) | Точное совпадение формулировок; короткий точный заголовок «Ремонт кофемашин» лучше длинного SEO-заголовка с теми же словами; устойчивость к опечаткам |
| Память train | BM25 расширения запроса словами из заголовков, выбранных по похожим запросам; P(подкатегория \| запрос) и её ранг; доля подкатегории в top-30 выдачи | Синонимы из реального поведения пользователей («трамбовочная машина» → «виброплита»); тематический prior |
| Нейросетевые | Косинус с запросом для трёх энкодеров, ранг и отставание от лучшего в локации | Семантика и перефразировки, которых нет в train |
| Локация | Доля переходов «локация поиска → локация объявления» в train; та же ли локация; расстояние до «центра» локации поиска | Услуги локальны; поиск по области ведёт в города области |
| Фильтры | Доля фильтров поиска, найденных в параметрах объявления; фильтр по рейтингу | Пользователь сам сузил выдачу |
| Объявление | Рейтинг, число отзывов, цена, скрытый телефон, запрет сообщений, категория, длина текста, популярность подкатегории в локации | Среди похожих выбирают «качественные» |
| Контекст запроса | Число слов, сходство с ближайшим запросом train, размер пула в локации, уверенность prior'а | Калибровка остальных признаков: у незнакомого запроса меньше доверия к «памяти» |
| Ранги | Ранги и нормировки основных скоров внутри локации | Относительная, а не абсолютная сила совпадения |

## 2. Модели и алгоритмы

1. **BM25** (`src/text_index.py`) — реализован вручную на `scipy.sparse`. Для каждого поля
   строится матрица «документ × стем» с BM25-весами, и скор запроса по всему корпусу получается
   как сумма нескольких столбцов за миллисекунды. Нормализация: нижний регистр, `ё→е`,
   стемминг Snowball (русский и английский).
   **Префиксное расширение:** если последнее слово запроса редкое, оно, вероятно, недописано,
   и тогда берётся максимум BM25 по словам с таким префиксом («прокат квад» → «квадроцикл»).
2. **kNN по запросам train** (`src/query_knn.py`) — 30 ближайших текстов из train по TF-IDF
   слов и символьных n-грамм. Из них берём распределение подкатегорий выбранных объявлений
   (top-1 угадывается в 66% случаев, top-3 — в 85%) и 15 самых частых стемов их заголовков
   для расширения запроса.
3. **Bi-encoder'ы** (`src/biencoder.py`), все работают на CPU:
   - `cointegrated/rubert-tiny2` (29M), **дообученная** на 228k парах «запрос → выбранное
     объявление» из train. Loss — симметричный InfoNCE с in-batch негативами (батч 128, без
     повторов запросов и объявлений в батче, не больше 30 пар на текст, чтобы популярные
     запросы не доминировали);
   - `sergeyzh/rubert-mini-frida` (32M, дистиллят FRIDA) **без дообучения** — общая семантика;
   - она же, **дообученная** тем же способом.

   В коротком тесте (344 запроса, правильный ответ среди ~100 кандидатов) mini-frida без
   дообучения ранжировала почти как дообученный tiny2 (MRR 0.317 против 0.329). Три энкодера
   дополняют друг друга: каждый из них — отдельный источник кандидатов и отдельный набор признаков.
4. **Пул кандидатов** (`src/candidates.py`) — объединение top-N из 7 источников:
   основной скор (BM25 + расширение + log P(подкатегории) + косинус tiny2) в «своих» локациях;
   чистый BM25; только расширение; top-100 по каждому из трёх энкодеров; основной скор без
   фильтра локации (онлайн-услуги, межгород). В среднем ~420 кандидатов, в них попадает
   96.6% правильных ответов.
5. **Ранкер** (`src/ranker.py`) — LightGBM `lambdarank` с отсечкой 60 позиций: метрике важно
   только попасть в top-50, порядок внутри не важен. Финальная модель — среднее 5 ранкеров
   с разными seed.

## 3. Как проверялось качество до отправки

**Локальная валидация повторяет устройство бенчмарка** (`src/build_dev.py`):
1. 5 фолдов по 2452 запроса. В каждой локации берётся столько запросов из train, сколько
   запросов бенчмарка в ней.
2. Текст внутри локации `s` выбирается с весом `n(текст, s) / n(текст)`, что эквивалентно
   «равномерно по уникальным текстам». Доля текстов, встречающихся в train, 0.358 (у бенчмарка 0.370).
3. Строки этих запросов и строки с их объявлениями убираются из train. Оставшаяся «fit»-часть
   (471k строк) — единственное, на чём строятся kNN, статистики и дообучаются нейросети.
   Поэтому их скоры на валидации честные.
4. Корпус фолда = корпус бенчмарка + правильные ответы запросов фолда. Ответы «спрятаны»
   среди тех же 189k объявлений, а их плотность такая же, как в бенчмарке.

Фолд f0 — валидация, f1–f4 — обучение ранкера. Recall@50 считается по полному списку
правильных ответов, в том числе тех, что не попали в пул. Для решений о признаках
использовался out-of-fold по всем 5 фолдам.

**«Трудное» подмножество как ориентир для лидерборда.** У запроса бенчмарка в корпусе есть его
собственная «выдача» из десятков похожих объявлений, а у dev-запроса её нет, поэтому dev легче.
Out-of-fold Recall@50, разбитый по сходству dev-запроса с запросом бенчмарка из той же локации:

| сходство | запросов | Recall@50 | потолок пула |
|---|---|---|---|
| ≤ 0.2 | 9119 | 0.946 | 0.962 |
| 0.2–0.4 | 2150 | 0.911 | 0.960 |
| 0.4–0.6 | 767 | 0.879 | 0.952 |
| > 0.6 | 219 | 0.871 | 0.945 |

Запросы со сходством > 0.4 конкурируют с реальной выдачей бенчмарка. Метрика на них (0.877)
оказалась лучшим предсказателем результата на платформе.

**История улучшений:**

| Шаг | f0 | OOF | «трудные» | платформа |
|---|---|---|---|---|
| BM25 по трём полям + фильтр локации | 0.661* | | | |
| + расширение запроса по kNN + prior подкатегории (ручные веса) | 0.721* | | | |
| Пул из нескольких источников + LightGBM | 0.903 | 0.900 | ~0.84 | 0.86 |
| + дообученный rubert-tiny2 (источник + признаки), префиксы, биграммы | 0.930 | 0.927 | 0.871 | 0.8933 |
| + rubert-mini-frida без дообучения, бэггинг 5 ранкеров | 0.932 | 0.930 | 0.875 | 0.8996 |
| + дообученная rubert-mini-frida | **0.940** | **0.935** | **0.877** | **0.9081** |

\* на первой версии валидации (см. ниже), сравнимо только между собой.

**Проверенные и отброшенные идеи:**
- `binary` вместо `lambdarank`: 0.924 против 0.932 на f0; большие деревья и ансамбли разных
  целевых функций тоже хуже.
- Валидация из «двойников» (`build_dev.py --twins`): для каждого запроса бенчмарка берутся
  5 самых похожих запросов train из той же локации, чтобы ранкер учился в условиях реальной
  выдачи. На «чистых» запросах (не входящих в dev другого варианта) ранкер, обученный на
  обычной валидации, оказался не хуже (0.927 против 0.923 и 0.912 против 0.908). Двойники
  к тому же вынимают из train самые полезные для бенчмарка запросы, поэтому вариант отброшен.
  На платформе он дал столько же, сколько основной (0.89).
- Ансамбль основного варианта и «двойников» по рангам (RRF) — без прироста.

## 4. Анализ ошибок и что с ними сделано

**Ошибки валидации** (самые опасные: из-за них можно улучшать не то):

| Проблема | Как найдена | Что сделано |
|---|---|---|
| Первая версия валидации (случайные запросы, ответы 15k запросов в одном корпусе) давала 0.889. Главные признаки ранкера — локационные. | Подозрительно близко к потолку пула. Сравнение числа объявлений на запрос в dev и в бенчмарке. | В городах, где у бенчмарка мало объявлений, вставленные ответы почти не имели конкурентов. Фолды выровнены по локациям бенчмарка, ответы вставляются по 2452 запроса на корпус. |
| После выравнивания по локациям доля «знакомых» текстов стала 0.785 против 0.370 у бенчмарка. | Сравнение со статистикой бенчмарка. | Взвешенная выборка текстов `n(текст, s) / n(текст)`: «маникюр», который ищут во всех городах, почти не попадает в dev. |
| Риск утечки через «снимок» объявлений: ответы dev берутся из train, остальное — из корпуса бенчмарка. | Сравнение полей 18k объявлений, общих для train и корпуса. | Все поля совпадают, утечки нет. |
| Dev легче бенчмарка: у запросов бенчмарка вдвое больше сильных конкурентов в своей локации (медиана 3 против 1 объявления с полным совпадением слов). | Сравнение статистик пулов dev и бенчмарка. | Введено «трудное» подмножество как ориентир; проверен вариант с «двойниками» (см. выше). |

**Ошибки модели** (разбор промахов на валидации):

| Тип ошибки | Пример | Доля / эффект | Что сделано |
|---|---|---|---|
| Ответ в «дочерней» локации | поиск по области, объявление в городе области | 17–24% ответов не в локации поиска | Матрица переходов локаций из train + расстояние до центра локации. Вне расширенного фильтра осталось ~3% ответов; для онлайн-услуг есть источник без фильтра локации. |
| Синонимы без общих слов | «мини кран» → «Аренда автовышки»; «трамбовочная машина» → «виброплита» | ~4% ответов с нулевым BM25 | Расширение запроса по похожим запросам train, три bi-encoder'а. |
| Недописанные запросы (обрыв автодополнения) | «прокат квад», «vip сопр» | единицы процентов | Префиксное расширение последнего слова. |
| Морфология и опечатки | «телевизоров», «мерсадес» | | Стемминг, символьные n-граммы. |
| Ложное расширение запроса | «виниры» → «Оклейка авто виниловой плёнкой» (через символьные n-граммы) | | Нейросетевые скоры как противовес. Ранкер видит сходство с ближайшим запросом train и меньше доверяет «памяти», когда запрос незнаком. |
| Правильный ответ среди десятков почти одинаковых объявлений | «Ремонт кофемашин» в Краснодаре: ~40 похожих объявлений | основной источник оставшихся ошибок: разрыв между потолком пула (0.966) и Recall@50 (0.940) | Признаки «точности» заголовка, биграмм, качества объявления; lambdarank с фокусом на top-60; бэггинг ранкеров; более сильные нейросетевые признаки. |

Итоговое распределение ошибок на f0: 3.4% правильных ответов не попадают в пул (из них около
трети — в «чужих» локациях, остальное — трудная семантика вроде «Ищу моделек» для запроса про
наращивание ногтей), 2.6% попадают в пул, но не проходят в top-50.

## Использованные open-source компоненты

- **pandas, pyarrow, numpy, scipy** — данные и разреженные матрицы (BM25 реализован на них вручную);
- **scikit-learn** — TF-IDF векторизаторы;
- **snowballstemmer** — стемминг русского и английского;
- **LightGBM** — ранкер (lambdarank);
- **PyTorch, transformers, huggingface_hub** — дообучение и инференс bi-encoder'ов (цикл обучения свой);
- **cointegrated/rubert-tiny2** и **sergeyzh/rubert-mini-frida** (HuggingFace, MIT) — модели эмбеддингов;
- идеи: BM25 (Robertson & Zaragoza), InfoNCE с in-batch негативами (MultipleNegativesRanking),
  pseudo-relevance feedback, взвешенная выборка без возвращения (Efraimidis–Spirakis).

Ответы не захардкожены под `query_id`: всё выводится из train и признаков запроса и объявлений.

## Структура

```
run_all.py            полный прогон от parquet до answer.csv
src/common.py         пути, загрузка, нормализация текста, метрика Recall@K
src/build_dev.py      валидационные фолды, fit-часть train, корпуса фолдов
src/fitdata.py        загрузка fit-части и режимов (фолд / бенчмарк)
src/text_index.py     BM25-индексы полей
src/query_knn.py      kNN по запросам train: prior подкатегории, расширение запроса
src/biencoder.py      дообучение bi-encoder'ов и эмбеддинги
src/dense.py          доступ к эмбеддингам в порядке корпуса
src/candidates.py     пул кандидатов и признаки
src/ranker.py         LightGBM-ранкер: валидация, финальная модель (бэггинг)
src/predict.py        answer.csv с проверками формата
src/fetch_models.py   загрузка весов моделей (релиз + HuggingFace с фиксированными ревизиями)
answer.csv            отправленный ответ (Recall@50 = 0.9081)
```
